\subsection{Actividad 1: Creacion de una casa sencilla con OpenGL}
Para construir la casa decidimos extender el mismo patrón que ya usábamos con la clase \texttt{Triangle3D}, en vez de armar una jerarquía nueva de clases. La idea fue simple: una casa vista desde estas prácticas no es más que un cubo (las paredes) con una pirámide de base cuadrada encima (el techo), así que creamos una clase \texttt{House3D} que arma exactamente esa geometría.

El constructor recibe dos parámetros, \texttt{size} (la mitad del ancho del cubo) y \texttt{roofHeight} (qué tan alto sobresale el techo respecto a la parte superior del cubo), y dejamos también un constructor de conveniencia que solo pide \texttt{size} y usa esa misma medida como altura del techo. Definimos 9 vértices en total: los primeros 8 corresponden a las esquinas del cubo (4 abajo y 4 arriba) y el noveno es el vértice donde convergen las cuatro caras del techo. Para que la figura quedara centrada en el origen, todas las coordenadas se calculan como desplazamientos de \texttt{size} respecto a $(0,0,0)$, de modo que sin importar qué tan grande o pequeña se haga la casa, su centro geométrico siempre cae en el origen.

Reutilizamos los vértices superiores del cubo como base del techo en vez de duplicarlos, lo que ahorra memoria pero implica que el color se interpola entre la pared y el ápice del techo. Aprovechamos esto a nuestro favor: le dimos a las paredes un tono claro y al vértice del ápice un tono rojizo, de modo que el degradado que genera OpenGL al interpolar los colores termina pareciendo un techo de color distinto, sin necesidad de duplicar geometría ni complicar el shader.

Los índices se organizaron por caras: dos triángulos para el piso, dos por cada una de las cuatro paredes, y cuatro más para las caras del techo (cada una toma una arista del cuadrado superior y la une con el ápice). Decidimos no dibujar la cara superior del cubo porque queda completamente tapada por el techo, evitando así geometría innecesaria.

\begin{lstlisting}[language=C, caption=Código de la construccion de la casa (House3D), label=lst:codigo-casa]
    void buildVertices(float size, float roofHeight) {

	// Color de las paredes (tono claro tipo naranja claro)
	float wr = 0.85f, wg = 0.80f, wb = 0.65f;

	Vertex v;

	// Paredes, 8 vertices
	// Cara inferior (y = -size)
	v.Position = vec3(-size, -size, -size); setColor(v, wr, wg, wb); vertices.push_back(v); // 0: fondo-izq-abajo
	v.Position = vec3(size, -size, -size); setColor(v, wr, wg, wb); vertices.push_back(v); // 1: fondo-der-abajo
	v.Position = vec3(size, -size, size); setColor(v, wr, wg, wb); vertices.push_back(v); // 2: frente-der-abajo
	v.Position = vec3(-size, -size, size); setColor(v, wr, wg, wb); vertices.push_back(v); // 3: frente-izq-abajo

	// Cara superior (y = size)
	v.Position = vec3(-size, size, -size); setColor(v, wr, wg, wb); vertices.push_back(v); // 4: fondo-izq-arriba
	v.Position = vec3(size, size, -size); setColor(v, wr, wg, wb); vertices.push_back(v); // 5: fondo-der-arriba
	v.Position = vec3(size, size, size); setColor(v, wr, wg, wb); vertices.push_back(v); // 6: frente-der-arriba
	v.Position = vec3(-size, size, size); setColor(v, wr, wg, wb); vertices.push_back(v); // 7: frente-izq-arriba

	// Techo, vertice 8
	v.Position = vec3(0.0f, size + roofHeight, 0.0f);
	setColor(v, 0.55f, 0.20f, 0.12f);
	vertices.push_back(v); // 8
    }

\subsection{Actividad 2: Configuración de las vistas: frontal, lateral y superior}
Para las tres vistas no fue necesario tocar la lógica de renderizado ni las matrices de proyección: bastó con manipular los tres vectores que recibe \texttt{glm::lookAt}, que ya estaban expuestos en el objeto \texttt{camera} (\texttt{Position}, \texttt{View} y \texttt{Up}). El código original ya tenía las teclas F1, F2 y F3 conectadas a bloques que modificaban esos vectores, pero al revisarlo notamos que las posiciones no correspondían a lo que pedía la práctica (una de las vistas quedaba en diagonal en vez de frontal, y las otras dos estaban intercambiadas entre lado y superior), así que rehicimos los tres bloques desde cero.

Colocamos la cámara sobre cada uno de los ejes principales, siempre apuntando hacia el origen, que es donde vive la casa: F1 sobre el eje $+Z$ para la vista frontal, F2 sobre el eje $+X$ para la vista lateral, y F3 sobre el eje $+Y$ para la vista superior. El único ajuste que requirió pensarlo dos veces fue el vector \texttt{Up} de la vista superior: como ahí la cámara mira directamente hacia abajo a lo largo del eje $Y$, no podíamos dejar \texttt{Up} apuntando también en $Y$, porque quedaría paralelo a la dirección de vista y \texttt{lookAt} no tendría forma de saber hacia dónde orientar la parte superior de la imagen. Resolvimos esto usando $(0,0,-1)$ como \texttt{Up} solo para esa vista, dejando $(0,1,0)$ para las otras dos.

\begin{lstlisting}[language=C, caption={Código de las vistas: frontal, lateral y superior}, label=lst:codigo-vistas]

if (glfwGetKey(window, GLFW_KEY_F1) == GLFW_PRESS) {
    // Vista frontal: camara sobre el eje +Z mirando hacia el origen
    camera.Position = glm::vec3(0.0f, 0.0f, 3.0f);
    camera.View = glm::vec3(0.0f, 0.0f, 0.0f);
    camera.Up = glm::vec3(0.0f, 1.0f, 0.0f); //rotacion
}
if (glfwGetKey(window, GLFW_KEY_F2) == GLFW_PRESS) {
    // Vista de lado: camara sobre el eje +X mirando hacia el origen
    camera.Position = glm::vec3(3.0f, 1.0f, 1.0f); // Lo modifique para que se viera el lado, ya que si lo pongo "literalmente" de lado, no habria diferencia entre el frontal y el lado debido a que son pares las caras 
    camera.View = glm::vec3(0.0f, 0.0f, 0.0f);
    camera.Up = glm::vec3(0.0f, 1.0f, 0.0f);
}
if (glfwGetKey(window, GLFW_KEY_F3) == GLFW_PRESS) {
    // Vista superior: camara sobre el eje +Y mirando hacia abajo
    camera.Position = glm::vec3(0.0f, 3.0f, 0.0f);
    camera.View = glm::vec3(0.0f, 0.0f, 0.0f);
    camera.Up = glm::vec3(0.0f, 0.0f, -1.0f);
}
\end{lstlisting}

\subsection{Actividad 5: Implementación de la camara usando WASD}

El proyecto base ya traía las teclas WASD asignadas, pero lo que hacían era sumar y restar cantidades fijas a las componentes \texttt{x} y \texttt{y} de la posición de la cámara. Eso mueve al observador sobre un plano, así que conforme uno recorre la escena la distancia a la figura va cambiando sola y la casa termina saliéndose del encuadre. Lo que queríamos era otra cosa: que A y D giraran alrededor del objeto sin acercarlo, y que W y S fueran las que se encargaran de acercar y alejar.

Para lograrlo dejamos de guardar la posición de la cámara en coordenadas cartesianas y la describimos con dos cantidades: un ángulo \texttt{camAngulo} medido sobre el plano horizontal y un radio \texttt{camRadio} que es la distancia al origen. Con eso la posición se recupera en cada cuadro como $x = r\cos\theta$ y $y = r\operatorname{sen}\theta$, mientras que la altura se queda fija en \texttt{camAltura}. La ventaja es que cada tecla toca una sola variable: modificar el ángulo recorre una circunferencia de radio constante, y modificar el radio acerca o aleja al observador siguiendo la recta que lo une con el origen. Como en nuestra figura el eje vertical es $z$, la órbita se desarrolla sobre el plano $xy$.

Las tres variables las declaramos como globales, junto al objeto \texttt{Camera}, porque las escribe la función que atiende el teclado y las lee la que dibuja. También ajustamos los argumentos del constructor: el punto de interés lo pusimos en el origen, ya que \texttt{glm::lookAt} espera ahí un punto y no un vector de dirección, y el vector vertical lo pusimos en $(0,0,1)$ para que el eje $z$ se despliegue hacia arriba de la ventana, que es como construimos la geometría de la casa.

El cálculo de la posición lo agregamos dentro de \texttt{Update}, justo antes de armar la matriz de vista. El orden ahí sí importa: como \texttt{glm::lookAt} recibe la posición del observador, si el cálculo se hiciera después de esa llamada la matriz correspondería a la posición del cuadro anterior y el giro se vería con un cuadro de retraso. La conversión a radianes es necesaria porque las funciones trigonométricas trabajan en esa unidad, aunque nosotros preferimos manejar los incrementos en grados por ser más fáciles de ajustar a ojo.

Por último, en \texttt{keyboardCallback} sustituimos las cuatro asignaciones originales por incrementos sobre el ángulo y el radio. Fue importante borrarlas y no solo agregar las nuevas: como la posición se recalcula en cada cuadro a partir del ángulo y el radio, cualquier valor asignado directamente a \texttt{camera.Position} queda sobrescrito antes de llegar a la pantalla y las teclas no harían nada. Los signos de A y D los decidimos probando, porque el sentido aparente del giro depende de dónde arranque el observador.

\begin{lstlisting}[language=C, caption=Código de la cámara orbital controlada con WASD, label=lst:codigo-camara]
// Declaracion de la camara y de los parametros de la orbita
Camera camera(glm::vec3(3.0f, 0.0f, 0.0f),
              glm::vec3(0.0f, 0.0f, 0.0f),
              glm::vec3(0.0f, 0.0f, 1.0f));

float camAngulo = 0.0f;
float camRadio = 3.0f;
float camAltura = 0.0f;

// Dentro de Update(): posicion del observador en cada cuadro
glm::mat4 projection = glm::perspective(glm::radians(45.0f),
        (float)screenWidth / (float)screenHeight, 0.1f, 1000.0f);

myShader->setMat4("projection", projection);

camera.Position.x = camRadio * cos(glm::radians(camAngulo));
camera.Position.y = camRadio * sin(glm::radians(camAngulo));
camera.Position.z = camAltura;

glm::mat4 view = glm::lookAt(camera.Position, camera.View, camera.Up);
myShader->setMat4("view", view);

// Dentro de keyboardCallback(): asignacion de las teclas
if (glfwGetKey(window, GLFW_KEY_W) == GLFW_PRESS) {
    camRadio -= 0.02f;
    if (camRadio < 0.1f)
        camRadio = 0.1f;
}
if (glfwGetKey(window, GLFW_KEY_S) == GLFW_PRESS) {
    camRadio += 0.02f;
}
if (glfwGetKey(window, GLFW_KEY_A) == GLFW_PRESS) {
    camAngulo += 0.2f;
}
if (glfwGetKey(window, GLFW_KEY_D) == GLFW_PRESS) {
    camAngulo -= 0.2f;
}
\end{lstlisting}

\subsection{Actividad 6: Implementación de las flechas del teclado con respecto al eje Z}

Para llevar a cabo esta actividad, el objetivo fue lograr que la figura se pudiera mover hacia adelante y hacia atrás a lo largo del eje $Z$ en tiempo real usando las flechas del teclado. En lugar de modificar directamente las coordenadas de cada uno de los vértices dentro de la clase de la geometría, se utilizó el concepto de transformación rígida de traslación mediante la matriz de modelo, lo cual permite desplazar todo el objeto completo sin alterar su forma original.

El primer paso consistió en ubicar la función \textbf{keyboardCallback} dentro de 02\_ViewportTransformations.cpp, que es donde el programa detecta qué teclas se están presionando en la ventana. En el código base que nos dieron, las flechas del teclado estaban configuradas para modificar la posición del modelo en los ejes $X$ y $Y$. Por ello, se modificó la lógica para que al mantener presionada la tecla de la flecha arriba (\texttt{GLFW\_KEY\_UP}) se le sumara un incremento constante de $0.01\text{f}$ a la componente en $Z$ de la variable \texttt{modelPosition}, logrando que la figura avance hacia el frente. De igual manera, se configuró la flecha abajo (\texttt{GLFW\_KEY\_DOWN}) para restar ese mismo valor en $Z$, haciendo que el objeto retroceda alejándose de la pantalla.

A continuación se muestra el fragmento modificado dentro de la función \texttt{keyboardCallback}:

\begin{lstlisting}[language=C++, caption={Control del desplazamiento sobre el eje Z con las flechas del teclado}]
// Ejercicio 6. Movimiento del objeto 3D en el eje Z
// Flecha Arriba: avanzar hacia el frente (+Z)
if (glfwGetKey(window, GLFW_KEY_UP) == GLFW_PRESS) {
    modelPosition.Position.z += 0.01f;
}

// Flecha Abajo: retroceder hacia el fondo (-Z)
if (glfwGetKey(window, GLFW_KEY_DOWN) == GLFW_PRESS) {
    modelPosition.Position.z -= 0.01f;
}

// Flechas Izquierda y Derecha (desplazamiento lateral en el eje X)
if (glfwGetKey(window, GLFW_KEY_LEFT) == GLFW_PRESS) {
    modelPosition.Position.x -= 0.01f;
}
if (glfwGetKey(window, GLFW_KEY_RIGHT) == GLFW_PRESS) {
    modelPosition.Position.x += 0.01f;
}
\end{lstlisting}

Finalmente, se revisó que dentro de la función \texttt{Update()} se estuviera calculando correctamente la matriz de modelo usando la función \texttt{glm::translate}. De esta manera, cada vez que cambia el valor de la posición en $Z$ por la entrada del teclado, la matriz se actualiza y se envía directamente al \textit{shader} antes de mandar a dibujar la malla con \texttt{Draw()}. 

\begin{lstlisting}[language=C++, caption={Aplicación de la traslación a la matriz de modelo dentro de Update()}]
// Aplicamos transformaciones del modelo (traslación rígida)
glm::mat4 model = glm::mat4(1.0f);
model = glm::translate(model, glm::vec3(modelPosition.Position.x, 
                                        modelPosition.Position.y, 
                                        modelPosition.Position.z));
model = glm::rotate(model, glm::radians(0.0f), glm::vec3(0.0f, 1.0f, 0.0f));
model = glm::scale(model, glm::vec3(1.0f, 1.0f, 1.0f));	
myShader->setMat4("model", model);

mesh->Draw(*myShader);
\end{lstlisting}
